# 下载增长与项目证据

目的：让有同类问题的人找到技能、完成第一次体验、愿意再次使用。当前是可执行计划，没有填写尚未发生的下载、用户或效果数据。

## 先解决哪一环

| 观察到的现象 | 优先动作 | 可验证的变化 |
|---|---|---|
| 曝光少 | 使用场景明确的标题/分类，围绕“有数据不知道做什么”发布真实案例 | 同口径的曝光/访问变化；平台不提供则记未知 |
| 浏览后不下载 | 首屏展示输入、产出、两版演示与安装条件 | 同来源、同统计周期的访问到下载比例；无访问分母不计算转化率 |
| 下载后无法用 | 修复导入/依赖/页面展示问题；补目标宿主实际步骤 | 自愿测试者中导入、读取、完成候选比较的实际人数及失败原因 |
| 用完一次不再用 | 收集真正需要的后续任务，完善续作与证据复用 | 经同意记录的二次使用，不推算未知用户行为 |

## 小规模启动安排

1. 先请3–5名目标用户自愿试用，学术/企业均覆盖；用平台、客户端版本、操作系统、提交SHA和步骤结果记录反馈。这个人数是试用计划，不是已有用户。
2. 修复会阻断首次体验的问题，再准备学术和企业各一份有授权的真实案例；没有真实案例时继续清楚标注合成演示。
3. 作者确认公开发布后提交SkillHub；按允许发布作品的社区规则分享“问题→输入→审核发现→候选取舍”的案例，链接指向实际页面。此计划不授权代理代发社区消息。
4. 每周保存平台后台或公开计数快照及截止时间，每轮先改一个主要因素（标题、首屏或演示）。自然流量的前后变化受渠道、曝光、节假日等影响，只作观察；有随机分流和足够样本才叫A/B测试。

## 统一计数口径

维护一张表：`记录时间 / 平台 / 发布页URL / 提交SHA / 下载计数 / 收藏计数 / 计数来源 / 备注`。保留原始后台导出或截图；区别下载请求、安装、独立用户和活跃用户。跨平台用户无法去重时只分别报告；平台来源混合或统计定义未知时如实注明。不把自己的自动验收或下载重试当作新用户。

本技能不植入下载上报、跟踪像素或用户数据遥测。平台计数与自愿反馈足以开始验证需求。

## 简历表达

当前可以写：

> 独立设计并实现 data-to-value 数据驱动选题与业务机会技能，支持学术/企业双流程、数据说明与实物核验、候选评分和用户决策；构建统一数据读取与安装验收，提供可复现回归测试和双场景演示。

上架并有证据后再补：

> 在 SkillHub 发布，累计获得【截至日期的平台下载次数】次下载、【收藏次数】次收藏；通过【实际人数】位目标用户试用，修复【有记录的关键问题】。

没有独立用户数据就写“次下载”；无录用或试点证据就不写“提升论文录用率”“为企业节省X万元”。面试可展示：GitHub提交、测试结果、一次真实审核发现、候选比较、用户反馈和迭代记录。
