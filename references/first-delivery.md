# 首次交付与续作

本文件规范呈现和恢复，不改变 SKILL.md 中的版本选择、偏好确认、数据审核及最终选择规则。

## 降低首次使用负担

- “有数据，帮我看看能做什么”就是充分的起点，不要求用户先提供选题或收益假设。首次一次确认学术版/企业版与权重；已有确认不再问。
- 第一步确认后，把缺少且会改变方向的问题合并到一次简短询问；已有文件能回答的先读，不发长问卷。合并设置页不能展示时，直接列两版维度和初始权重，请用户一次选版并调整或明确接受；不要循环尝试弹窗。
- 用户只要想法时，默认做到候选比较与用户选择。不得以“完整流程”为由先跑模型或写长篇论文。
- 已有可用证据后，先呈现最小有用交付：审核摘要、实质不同的候选卡、比较和选择入口。过程中的完成状态只在发生有意义变化时用一句话说明。
- 用户没有数据且明确想体验时，展示 examples/README.md 中对应版本的合成样例。体验不证明对真实业务有效，也不记为真实项目或真实偏好确认。

## 第一份候选交付

先用三句话说明：读了哪些资料及范围；哪些事实可用；哪些冲突/未知限制了判断。随后按需展示候选卡，默认精选三个，不足不补造。

每张卡优先展示这些内容，展开材料再放完整细则：

| 内容 | 应回答的问题 |
|---|---|
| 一句话想法 | 用哪些数据回答什么问题，谁会使用答案？ |
| 证据与边界 | 哪个字段/文档/结果支持它，哪些仍是假设？ |
| 为什么值得做 | 学术新增量或业务动作是什么？未查新不确认创新度。 |
| 最简单基线 | 不用复杂模型时怎么做？ |
| 最小验证 | 哪个未知最影响去留，先检查什么；成立与不成立分别怎么办？ |
| 投入与风险 | 同一口径的时间/成本估算、关键依赖、失败后的有效交付。 |

若存在候选合并、前置依赖或重要淘汰方向，用短表交代原因，避免让用户把同一方案的三个步骤当成三种选择。

评分遵循 candidate-scoring.md：未知留空、不伪造总分、硬伤不参与排名。展示后请用户选候选编号，也可回复“先补某项证据”“调整约束重新找”或“暂不选”。不要只给一个强制接受推荐的按钮。

## 断点续作

长任务或即将中断时，在用户项目的可写工作区维护一份 `data-to-value-progress.md`；短任务可直接在对话交接，不强制建文件。只记录：

1. 本轮目标、版本及用户选择的原话/记录位置。
2. 已确认偏好、约束、已选方案；未确认项明确写“待用户确认”。
3. 数据路径/版本、已读取范围、证据输出位置、冲突和未知。
4. 已完成、正在做、下一步；运行环境回执位置（存在时）。
5. 当前等待的用户决定或外部条件，以及仍可独立推进的工作。

恢复时只核对会影响本轮的版本与证据，不重新索取已有选择或重做全库审核。文件中出现“用户已确认”但没有可追溯记录时，不将其当作新的授权。不复制原始敏感数据或凭证进交接文件。

## 能力不足时仍可提供什么

宿主能读取文件、但不能执行脚本时，基于实际读到的内容提供文字审核和比较，标明未执行的统计检查；宿主也不能读取文件时，仅给条件性框架。无论哪种情况，都不能把全文粘贴当成已运行统一读取器，也不在日常使用中临时安装依赖。
